# UI 优化的方法论

> 全部来自 2026-09-11 星河宠记全站视觉优化实战（今天 / 创作 / 时光 / 宠物档案 / 我的 / 家庭 + 27 张品牌插画）。
> **每条都对应一个真实踩过的坑和实测数据**，不是通用套话。原则后面括号里是"怎么发现的"。

---

## 一、先判断：什么叫"好看"

### 1. 好看 ≠ 元素多，而是**成体系**

用户最初的判断是"我们图片不够多，人家 UI 做得好"。核查结果是：**7 张插画自己就有两套风格**——品牌 IP 是 3D 黏土，登录主视觉的生成提示词写的是"柔和扁平"。
**在打架的基础上加图，只会更乱。**

> 动作：先找出现有素材里的**风格冲突**，定成一套，再谈加法。

### 2. "修好了"不等于"变好看了"

给全站做了 464 处 CSS 修复，按 alpha 分档统计：

| alpha | 处数 | 占比 | 肉眼 |
| --- | --- | --- | --- |
| ≤0.15 | 238 | 51% | 基本看不出 |
| 0.15~0.3 | 161 | 35% | 基本看不出 |
| 0.3~0.6 | 49 | 11% | 可感知 |
| >0.6 | 8 | 2% | 明显 |

**86% 的修复是"本该有的淡色底没渲染出来"，修好了也只是本该如此。**

> 动作：汇报时**必须把"修复"和"美化"分开说**，否则会让对方以为全站都优化了，实际没有。

### 3. "改了"不等于"看得出来"

第一版给"今日/更多"卡片只加了图标色底（alpha 0.12），用户反馈**"怎么没有变化"**。第二版把卡片本身也加上淡色底 + 同色边框，才一眼可辨。

> 动作：视觉改动按**"用户一眼能不能分辨"**定幅度，不是按"代码里改了几行"。

### 4. 空态不是主战场

全项目 74 处空态，但**空态只有"没有数据"的用户才看得到**，有数据的老用户永远触发不到。
（这一条直接解释了用户为什么觉得"其他页面一点变化没有"。）

> 动作：优先级 = **始终可见的区域（页头、顶部卡片）> 有数据才出现的区域 > 空态**。

## 二、设计原则（可执行清单）

| # | 原则 | 为什么（实测） |
| --- | --- | --- |
| 1 | **一个页面只应有一个页头** | 时光页当时叠了"可乐的时光线 + 记录按钮"和"时光 + 说明"两套标题，用户：「冲突了，融合一下」 |
| 2 | **页头只写页面名，不写对象名** | 多宠物场景下页头挂"可乐的时光线"，切到布丁后立刻失效。改为"时光线"，对象名交给页面内切换器 |
| 3 | **卡片内容要和所在区块语义对位** | "今日健康分"卡放在「创作」页最顶上，用户：「挪到今日下面，不然真的太奇怪了」 |
| 4 | **控制器与被控对象必须相邻** | 宠物切换器换宠物 → 宠物卡的头像/名字/健康分跟着变，两者本就该放一起 |
| 5 | **图标色与底色必须同源** | 底色 `rgba(var(--x-rgb), α)`、图标走对应 `tone`。写死 hex 会出现"底变色、图标不变" |
| 6 | **颜色一律走主题变量，不写死** | 写死 `#ffd9b8` 在深色主题（星空银河）下会与整页脱节 |
| 7 | **位图按原始比例放，别硬铺** | 16:9 插画塞进 4:1 的框，`aspectFill` **裁掉约 55% 画面高度**（猫头被切） |
| 8 | **给位图配底色，先采样位图真实边缘色** | 我用品牌主色淡粉给插画横幅打底，与插画奶油底形成**一条硬接缝**（用户：「这一块看起来很奇怪」）。实测所有插画右边缘都在 `#F8C69F~#FDD1AE`，取该色即无缝 |
| 9 | **在图上叠文字时，遮罩按文字起始位置定** | "主体偏左"只是大致约定，实测主体会伸到画面 60%。遮罩要在文字起点就接近全实，不能按"大概一半" |
| 10 | **空态/缺省态必须有视觉主体** | 74 处空态里只有 8% 有图，其余是"一行字 + 小图标" |
| 11 | **按钮要有：渐变 + 投影 + 圆角胶囊 + 按压动效 + 图标** | 用户明确偏好；悬空的裸「＋」圆圈被评价为"像没归属的浮标" |
| 12 | **警惕假按钮** | 卡片里的「＋添加照片」有按钮样式和按压反馈，但点击只打开详情、根本不支持补照片——点不出预期结果 |
| 13 | **清理死代码与时序耦合** | 组件接入后要删掉页面原有的 padding/居中样式：两边都是单类选择器，冲突时谁生效取决于编译后样式表顺序，**不能赌** |

## 三、怎么确认"真的变好看了"（最痛的部分）

### 铁律：**截图会骗人，`getBoundingClientRect` 不会**

- 我据截图判断"创作页横向溢出"，差点去改一个不存在的 bug。
- 用 iframe 固定 375px 视口实测：`body.scrollWidth = 375`、`OVERFLOW = NO`、各元素 `right ≤ 349` —— **根本没有溢出**。
- 根因是截图工具本身：`--force-device-scale-factor=2` + `--window-size=375` 让页面按**约 208px 视口**布局，整批图失真。

### 完整验证链路（本项目已验证可用）

1. `npm run build:h5`（要 mock 数据就加 `TARO_APP_USE_MOCK=true`）
2. 本地静态服务托管 `dist-h5`
3. **注入格式合法的假登录态**绕过守卫（本项目 `isTokenFormatValid` 只校验三段结构 + exp、不验签）
   - ⚠️ Taro H5 的 storage 是 `localStorage[k] = JSON.stringify({ data })` 包装，写裸值会被解析成 undefined
   - ⚠️ Edge 无头模式下 localStorage **不跨进程持久化**，必须"写存储 → 同进程内跳转"
4. **把应用装进固定 375px 的 iframe 再截图**（绕开 CLI 视口 bug），同时用它量 DOM
5. 构建会清空 `dist-h5`，调试页要每次重建

### 验收时的三个反直觉点

- **别用 VLM 做细粒度一致性判据**：让视觉模型逐格描述 20 张插画的猫鼻/狗鼻，它给出了**几乎逐字相同的模板化回答**（还把狗说成三角鼻），证明它没在看。改为人工看图。
- **复核图的画布尺寸要按内容行数算**：写死 900px 高，10 张空态只截到前 6 张——**把"没看到"伪装成"没问题"**。
- **抓完图先看文件大小**：正常页面 130KB+，错误页 20~30KB。一眼识别失败，比逐张看快得多。

## 四、用 AI 生成视觉素材时

| 要点 | 实测教训 |
| --- | --- |
| **角色一致性靠双保险** | ① 把品牌 IP 当**参考图**喂模型（Seedream 4.0 支持 `images` 数组）② 提示词里**逐字重复角色锚点** |
| **锚点必须写到"品种级"并补排除项** | 只写"奶油色卷毛小狗"太含糊 → 某张被画成**巴哥犬**（扁脸、黑面罩、满脸褶子），角色直接断掉 |
| **提示词里绝不能出现引号包裹的文案** | 写了 `表达"还差一位家人"` → 模型**把那句话烧进了画面** |
| **先出验证批次，再批量** | 先出 4 张差异极大的场景确认角色稳定，再批量 24 张 |
| **必须先压缩再上线** | 直出 1024px 单张 300~380KB；缩到 600px + q86 → **8.9MB → 1.6MB（省 82%）**，全部 ≤100KB |
| **确认小程序的包体上限** | 主包已 1.81MB / 2MB（91.8%），24 张图塞不进 → 必须走服务器托管（`/uploads/`，注意 `CORP` 头要 `cross-origin` 否则跨域 `<img>` 一律被拦） |

## 五、协作与工程纪律

1. **多会话改同一仓库有覆盖风险**：动共用文件前先看 `git status` + 文件修改时间。本会话中 `PageHero.scss` 就被另一会话改过字号。
2. **用户指着截图说"这个"时，先确认是整块还是单个**：我犯了两次——只改标题没改按钮、只挪卡片没挪切换器。
3. **批量脚本先 dry-run，再单文件试点，再全量**；改完**用计数/grep 复核**（我曾把"删除"做成"复制"，靠"某函数出现 2 次"才发现）。
4. **结构性编辑后必查残留**：旧类名在 tsx 清零 ≠ scss 也清了（样式会变成死代码）。
5. **验证要跑全套**：`typecheck` + `build:weapp` + 全量测试 + 产物核验（引用是否入包、旧资源是否清除）+ 包体积。

## 六、一句话版

> **先做风格诊断而不是加法；改始终可见的区域；颜色和图标同源；位图不硬铺、底色采边缘；改动幅度按"一眼能否分辨"定；布局靠量不靠看；AI 素材先锁定角色再批量。**
